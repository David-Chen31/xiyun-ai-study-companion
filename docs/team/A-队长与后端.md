# A 的五天任务书｜让整套软件跑起来

你是队长，也负责写后端。第五天，把软件交给 C，请他在一台干净的电脑上照说明启动、导入一份作业、打开练习页。这个过程能独立走完，才算你交付成功。

## 开工先做这三件事

1. 确认 B、C 都能访问团队仓库。在 GitHub 为三人各开一张当天任务卡（Issue），写明今天收工前要看到的结果。
2. 给 B 一份固定的三句作业样例，放在你维护的 contracts/。约好时间统一用整数毫秒。例如第二句从 4000 开始听过门，5000 进入乐句，8000 结束。即使你的服务还没写好，B 也能拿样例开工。
3. 你负责协调老师和独立复核人，取得 WAV、三句时间表、署名与许可引用。向 C 只发送已获准处理的示范和句表。先用测试材料跑程序；真实发布时检查许可、到期日和独立复核。

你主要改 backend/、数据库、启动脚本、根目录配置和共享样例。B 交给你可打包的网页，C 交给你内部 HTTP 服务及测试样例。网页操作问题由 B 修，唱词和标注问题由 C 核实。

## 五天怎么做

|日期|按这个顺序做|今天交什么、给谁验|
|---|---|---|
|第 1 天|先让本机服务能启动，再让读取作业的地址返回三句样例。通过 HTTP 实际调用一次 C 的服务。|给 B 本机启动方法、作业编号和读取地址。让 B 在自己的网页上读出三句。|
|第 2 天|写导入命令。先查许可和复核人，再通过内部 API 请 C检查音频与句界；通过后一起保存录音和句表。加上播放和撤回功能。|给 C 一套可复制的导入、打开、撤回命令。用同一包导入两次只出现一份作业；试一份坏包，原作业仍可打开。|
|第 3 天|把 B 编好的网页放进本机服务，从同一个入口打开。每次读取作业或请求音频时检查是否失效，重启后保留撤回状态。|给全队一个真实作业链接。现场走完打开、试听、录音、回听、接续和撤回，再让 C 用旧音频地址重试。|
|第 4 天|让 C 在干净环境安装，你旁观并记下他卡在哪一步。修安装、文件位置和启动问题，留存当天通过测试的版本。|交一份启动说明草稿和可回退的版本号。别人仅凭说明就能启动、停止并重新启动。|
|第 5 天|合入已复测的修复，标记交付版本。用下载的交付包再演示一遍，核对 B 的网页结果和 C 的整套测试结果。|给团队下载地址、版本号、启动/停止/重置说明、演示素材领取方式、已知问题。受限原件及凭证走受控渠道。|

## 你最容易漏的两处

- **界面能打开，音频却不能播放。** 把作业编号、音频地址和服务返回结果发给 B。先自己试一次取音频及拖到中段播放，再一起查浏览器。
- **撤回后仍能拿到音频。** 除了打开旧作业页，还要直接用之前的音频地址重新请求；重启服务后再试一次。两个入口都要拦住。

## 交付前逐项核对

- [ ] B 能说明从哪个地址拿唱词、时间和音频；C 能按你的命令导入和撤回。
- [ ] 同一作业重复导入、许可缺失、时间越界、许可过期、服务重启都测过，坏输入不会破坏原作业。
- [ ] 干净环境能运行，学员原声只留在浏览器；最终下载地址和测试记录对应同一个版本。
- [ ] 每次合并前有队友检查，合并后自己打开一次作业。遇到阻塞，在任务卡上写“谁接手、需要什么、何时再试”。

## 技术设计与长期职责

先读[全功能覆盖表](TEAM_PLAN.md)和[双端 API 契约](API_CONTRACT.md)。你维护业务库、许可、私有媒体、发布快照、内外接口适配及根启动脚本。C 的服务独立启动，只处理教师示范。确认返回修订匹配并重新校验许可后再提交事务；超时保留可重试状态，旧作业继续播放。

你可自主选择数据库表结构、事务与日志实现；交付数据流说明、接口成功/失败样例、安装与回退步骤。对外字段、访问范围、媒体留存、任务状态、产品流程变化由三方共同评审。平台阶段由你继续承接身份班级、教师上传/校订/审核、版本映射、进度与知识权限；AI 任务由你登记、授权、采纳、撤销，C 负责计算。最终由你核对每个 F 编号的验收证据，区分已交付和待验证。
